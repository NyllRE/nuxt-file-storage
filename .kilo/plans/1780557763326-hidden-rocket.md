# v0.4.0 — Multipart Upload Refactor Plan

## Branch
`refactor/multipart-storage-mode` (from `master` v0.3.3)

---

## 1. Breaking Changes (v0.3.x → v0.4.0)

| # | Change | Impact | Mitigation |
|---|--------|--------|------------|
| B1 | `clearOldFiles` → `deleteOldFiles` | Existing `useFileStorage()` calls with option get TS error | Keep `clearOldFiles` as deprecated alias |
| B2 | `storeFileLocally` → `storeFile` (accepts `ServerFile` directly) | Server code imports break | Keep `storeFileLocally` as deprecated wrapper calling `storeFile` |
| B3 | Default `storageMode` changed to `'Multipart'` | `files` ref API stays identical in both modes — `file.data` is always a blob URL. Only `submit()` behavior changes (FormData vs JSON). | Users wanting old DataURL body shape set `storageMode: 'DataURL'` |
| B4 | `ClientFile.data` changed from DataURL string to blob URL | v0.3.x `file.data` was a DataURL (`data:image/...`). v0.4.0 always uses a `blob:` URL. | Use `file.name`, `file.size`, etc. for metadata. Use `<img :src="file.data">` for previews. |
| B5 | `ServerFile` field renamed: `content` → `data`, type widened | v0.3.x had `content: string` (DataURL). v0.4.0 has `data: Buffer \| string` — Buffer for multipart, string for JSON. Matches `ClientFile.data`. |
| B6 | Composable signature changed | `useFileStorage(options)` → `useFileStorage(inputRef, options)`. `handleFileInput` removed — composable watches the input ref internally. |

## 3. Composable Design (`useFileStorage.ts`)

### New signature — ref-based, no `handleFileInput`

```typescript
type MaybeInputRef = Ref<HTMLInputElement | null> | HTMLInputElement | null

export default function useFileStorage(
  inputRef: MaybeInputRef,
  options: Options = {}
): UseFileStorageReturn
```

Internally wraps in `ref()` if not already a ref, so users can pass template refs, raw elements, or `null` interchangeably.

The composable takes the input element ref directly, watches it for mount, and attaches an internal `change` event listener. No `@input="handleFileInput"` needed in templates.

**Template usage:**
```vue
<input ref="inputRef" type="file" multiple />
```
```ts
const { files, clearFiles, submit } = useFileStorage(inputRef)
```

### Options

```typescript
type Options = {
  deleteOldFiles?: boolean
  /** @deprecated use deleteOldFiles */
  clearOldFiles?: boolean
  storageMode?: 'Multipart' | 'DataURL'  // default: 'Multipart'
  onProgress?: (percentage: number) => void  // default global progress handler
}
```

No `fileInputRef` option — the ref is the first argument.

### Return Type

```typescript
interface UseFileStorageReturn {
  files: Ref<ClientFile[]> & Iterable<ClientFile>
  clearFiles: () => void
  submit: (endpoint: string, opts?: SubmitOptions) => Promise<any>
}
```

`clearFiles()` always clears both the internal array and the input element's value (since the composable owns the ref).

### Internal state

```typescript
const clientFiles = createIterableRef<ClientFile>([])  // exposed as `files`
const nativeFiles: File[] = []                          // raw File objects for submit()
```

### Input watching

```typescript
let cleanUp: (() => void) | null = null

watch(inputRef, (el, oldEl) => {
  if (cleanUp) cleanUp()
  if (!el) return

  const handler = (event: Event) => {
    const target = event.target as HTMLInputElement
    if (!target.files?.length) return
    if (shouldDeleteOld) clearFiles()

    for (const nativeFile of target.files) {
      clientFiles.value.push({
        name: nativeFile.name,
        size: nativeFile.size,
        type: nativeFile.type,
        lastModified: nativeFile.lastModified,
        data: URL.createObjectURL(nativeFile),
      })
      nativeFiles.push(nativeFile)
    }
  }

  el.addEventListener('change', handler)
  cleanUp = () => {
    el.removeEventListener('change', handler)
    cleanUp = null
  }
}, { immediate: true })
```

### clearFiles — deferred blob URL revocation

```typescript
const clearFiles = () => {
  const oldUrls = clientFiles.value.map(f => f.data)

  clientFiles.value.splice(0, clientFiles.value.length)
  nativeFiles.length = 0

  // Reset input value
  const el = unref(inputRef)
  if (el) el.value = ''

  // Revoke after DOM has flushed (Vue batch update)
  nextTick(() => oldUrls.forEach(url => URL.revokeObjectURL(url)))
}
```

Revocation is always deferred to `nextTick` — whether called internally (from the change handler on `deleteOldFiles`) or externally by the user. This prevents broken preview images during DOM reconciliation.

### submit — The Core Design

```typescript
const submit = async (
  endpoint: string,
  opts?: SubmitOptions & Omit<FetchOptions, 'body'>
): Promise<any>
```

Where `SubmitOptions` extends the plan with timeout control and both modes support `extraBody`:

```typescript
type SubmitOptions = {
  extraBody?: Record<string, any>
  onProgress?: (percentage: number) => void
  timeout?: number            // XHR timeout in ms (default: none)
  signal?: AbortSignal
}
```

#### Multipart path — FormData with parallel JSON metadata for `lastModified`

```typescript
if (isMultipart) {
  const formData = new FormData()
  for (const file of nativeFiles) {
    formData.append('files', file)
  }

  // Preserve lastModified + extraBody as a parallel JSON field
  const meta: Array<{ name: string; lastModified: number; size: number; type: string }> =
    nativeFiles.map(f => ({
      name: f.name,
      lastModified: f.lastModified,
      size: f.size,
      type: f.type,
    }))
  formData.append('_filesMeta', JSON.stringify(meta))

  if (extraBody) {
    for (const [key, value] of Object.entries(extraBody)) {
      formData.append(key, typeof value === 'object' ? JSON.stringify(value) : String(value))
    }
  }

  if (progressCb) {
    return new Promise((resolve, reject) => {
      const xhr = new XMLHttpRequest()
      if (timeout) xhr.timeout = timeout

      const onAbort = () => xhr.abort()
      if (signal) {
        if (signal.aborted) return reject(new DOMException('Aborted', 'AbortError'))
        signal.addEventListener('abort', onAbort)
      }

      xhr.upload.onprogress = (e) => {
        if (e.lengthComputable) progressCb(Math.round((e.loaded / e.total) * 100))
      }
      xhr.onload = () => {
        if (signal) signal.removeEventListener('abort', onAbort)
        if (xhr.status >= 200 && xhr.status < 300) {
          try { resolve(JSON.parse(xhr.responseText)) }
          catch { resolve(xhr.responseText) }
        } else {
          reject(new Error(`Upload failed (${xhr.status}): ${xhr.statusText}`))
        }
      }
      xhr.onerror = () => {
        if (signal) signal.removeEventListener('abort', onAbort)
        reject(new Error('Upload failed — network error'))
      }
      xhr.ontimeout = () => {
        if (signal) signal.removeEventListener('abort', onAbort)
        reject(new Error('Upload timed out'))
      }
      xhr.open('POST', endpoint)
      if (fetchOptions.headers) {
        for (const [k, v] of Object.entries(headersToRecord(fetchOptions.headers))) {
          xhr.setRequestHeader(k, v)
        }
      }
      xhr.send(formData)
    })
  }

  return $fetch(endpoint, {
    method: 'POST',
    body: formData,
    ...fetchOptions,
  })
}
```

Key design decisions:
- **`formData.append('files', file)`** — single field name for all files (not filename as key). Avoids ambiguity with duplicate filenames.
- **`_filesMeta`** — parallel JSON field preserves `lastModified` without filename mangling.
- **`extraBody`** — appended as individual form fields.
- **XHR cleanup** — `removeEventListener('abort', onAbort)` on every terminal event (load, error, timeout). No listener accumulation on retries.

#### XHR path limitation: ofetch interceptors are bypassed

When `onProgress` is provided, the request uses `XMLHttpRequest` instead of `$fetch`. This means:
- `onRequest`, `onRequestError`, `onResponse`, `onResponseError` ofetch hooks are NOT invoked
- Globally configured `$fetch.create()` defaults (headers, baseURL, retry) are NOT applied

Mitigation: If the user has configured global `$fetch` defaults (detected via a tag/flag they must explicitly set), warn in dev mode. Document this clearly.

#### DataURL path — serialization at submit time

```typescript
// DataURL mode — extraBody merges into JSON body, onProgress ignored
const serialized = await Promise.all(
  nativeFiles.map(file => fileToDataUrl(file).then(data => ({
    name: file.name, size: file.size, type: file.type,
    lastModified: file.lastModified, data,
  })))
)
return $fetch(endpoint, {
  method: 'POST',
  body: { files: serialized, ...(extraBody ? extraBody : {}) },
  ...fetchOptions,
})
```

`fileToDataUrl` wraps `FileReader.readAsDataURL`. Progress tracking is not supported in DataURL mode (encoding happens before the request; `onProgress` is silently ignored).

## 4. Server Utils (`storage.ts`)

### Unified `storeFile` — with MIME-to-extension fallback

```typescript
export const storeFile = async (
  file: ServerFile,
  fileNameOrIdLength: string | number,
  filelocation: string = ''
): Promise<string> => {
  const ext = file.name.includes('.')
    ? (file.name.split('.').pop() as string)
    : extFromMime(file.type)   // fallback: image/png → 'png', text/plain → 'txt', etc.

  let buffer: Buffer
  if (typeof file.data === 'string') {
    const parsed = parseDataUrl(file.data)
    buffer = parsed.binaryString
    // If filename had no extension AND ext wasn't resolved from MIME above,
    // fall back to the DataURL MIME extension
    if (!ext && parsed.ext) ext = parsed.ext
  } else {
    buffer = file.data
  }

  return writeToFileSystem(buffer, fileNameOrIdLength, filelocation, file.name, ext)
}
```

With a minimal MIME-to-extension map:

```typescript
const MIME_EXT_MAP: Record<string, string> = {
  'image/png': 'png',
  'image/jpeg': 'jpg',
  'image/gif': 'gif',
  'image/svg+xml': 'svg',
  'image/webp': 'webp',
  'text/plain': 'txt',
  'text/html': 'html',
  'text/css': 'css',
  'text/javascript': 'js',
  'application/json': 'json',
  'application/pdf': 'pdf',
  'application/zip': 'zip',
  'application/xml': 'xml',
  'audio/mpeg': 'mp3',
  'audio/wav': 'wav',
  'video/mp4': 'mp4',
  'video/webm': 'webm',
  // generic fallback from MIME subtype
}

const extFromMime = (mime: string): string => {
  if (!mime) return ''
  return MIME_EXT_MAP[mime] || mime.split('/')[1] || ''
}
```

The `writeToFileSystem` helper (shared, unchanged from v0.3.x) handles extension validation + mkdir + write.

### `multipartToServerFiles` — filters file parts, parses `_filesMeta`

```typescript
export const multipartToServerFiles = async (
  event: H3Event
): Promise<ServerFile[]> => {
  const parts = (await readMultipartFormData(event)) || []

  // Extract metadata from parallel JSON field, if present
  const metaField = parts.find(p => p.fieldName === '_filesMeta')
  const metaByName = new Map<string, { lastModified: number }>()
  if (metaField) {
    const arr: Array<{ name: string; lastModified: number }> = JSON.parse(metaField.data.toString())
    for (const m of arr) {
      if (m.name) metaByName.set(m.name, { lastModified: m.lastModified })
    }
  }

  return parts
    .filter(p => p.fieldName === 'files' && p.filename)   // only actual file parts
    .map(part => {
      const meta = part.filename ? metaByName.get(part.filename) : undefined
      return {
        name: part.filename || 'file',
        size: part.data.length,
        type: part.type || 'application/octet-stream',
        lastModified: meta?.lastModified ?? Date.now(),
        data: part.data,
      }
    })
}
```

Only parts with `fieldName === 'files'` and a `filename` are mapped. Other form fields (e.g., `_filesMeta`, `extraBody` entries) are excluded.

## 7. Migration Strategy

### What breaks silently (no TS error but behavior changes):

- `files.value[i].data` changes from DataURL string to `blob:` URL
- Composable signature changes — `handleFileInput` no longer returned
- `submit()` now sends multipart by default instead of JSON

### What needs user action:

| Scenario | Migration |
|----------|-----------|
| `useFileStorage()` with options | → `useFileStorage(inputRef, options)` |
| `@input="handleFileInput"` on `<input>` | → Remove event handler; composable watches ref internally |
| `useFileStorage({ clearOldFiles: false })` | → `{ deleteOldFiles: false }` |
| `storeFileLocally(file, 8, '/folder')` | → `storeFile(file, 8, '/folder')` |
| Wants old DataURL behavior | → `{ storageMode: 'DataURL' }` |
| `clearFiles(inputRef)` with override | → `clearFiles()` — composable owns the ref |

## 10. Data Flow Diagrams

### Multipart mode (default)
```
Browser File  →  URL.createObjectURL → blob: URL for preview
             →  File stored in nativeFiles[]
submit():
  nativeFiles[] → FormData.append('files', file) × N
                → FormData.append('_filesMeta', JSON.stringify([...]))
                → FormData.append(extraBody keys) × N
                → $fetch or XHR → multipart/form-data
    Server:
      readMultipartFormData(event) → multipartToServerFiles(event)
        → filter p.fieldName === 'files' && p.filename
        → match _filesMeta JSON for lastModified
        → ServerFile[] → storeFile(file, ...) → writeFile
```

### DataURL mode
```
Browser File  →  URL.createObjectURL → blob: URL for preview
             →  File stored in nativeFiles[]
submit():
  nativeFiles[] → Promise.all(nativeFiles.map(f => fileToDataUrl(f)))
                → { files: [{..., data: "data:..."}], ...extraBody }
                → $fetch → JSON body
    Server:
      readBody → ServerFile[] with data as DataURL strings
      → storeFile(file, ...) → typeof data === 'string'
        → parseDataUrl → Buffer → writeFile
```

## 12. Open Questions

1. **`inputRef` ergonomics**: The ref must be a live `Ref<HTMLInputElement | null>`. If users use `template ref` (which Nuxt auto-creates), this works. Should we support passing a raw `HTMLInputElement` (not ref) for static SSR scenarios? Probably not needed — user can wrap in `ref()`.

2. **Multiple input fields**: Users with multiple `<input type="file">` elements need multiple `useFileStorage()` instances — each gets its own ref. This is clearer than the old API where a single composable managed one implicit input. Confirm this is acceptable.

3. **`_filesMeta` field name collision**: If a user has a form field or `extraBody` key named `_filesMeta`, it conflicts with the internal metadata field. Should the metadata field use a more obscure name (e.g., `___nfs_meta___`), or document the reserved name?
